# Feature comparison: Claude Code, Pi, OMP (2026-10-23)

Scope: features beyond the CPU and RAM numbers in `harnesses/docs/FINDINGS.md`, and the port gaps in `harnesses/docs/PORTING.md` (not redone here). Evidence is the source clones, their docs, and `--help` output only; no network calls. Paths: Pi docs are under `~/checkout/pi-mono/packages/coding-agent/docs/` (abbreviated PI/ below), OMP docs under `~/checkout/oh-my-pi/docs/` (OMP/ below). Claude Code evidence is `claude --help` (v2.1.292) and a local settings file. Claude Code is closed source, so anything not visible in `--help` or local files is marked **unverified** (from general knowledge only).

Versions: Claude Code 2.1.292, Pi 1.4.0 (`<agent-storage>/NewHarness/build/pi/node_modules/.bin/pi --help`), OMP 18.12.6 (`<agent-storage>/NewHarness/build/omp/node_modules/.bin/omp --help`).

## Headline

Pi is a deliberately small harness: four default tools, no permission prompts, no subagents, no plan mode, no memory, and a TypeScript extension API for adding any of those yourself. OMP is a maximal fork of the same lineage (same MIT lineage and copyright) with nearly everything built in: hashline edits, subagents, LSP, approval tiers, plan mode, memory backends, a Rust native layer. Claude Code sits between them on features and is the only one with the shell-command hook contract, the permission allow/deny rule language and the managed/enterprise settings the tested safety guards depend on.

## Notes on rows that need them

Edit mechanism. Hashline's tag forces the model to re-read after any change, which prevents stale-context edits but costs extra reads; OMP ships a benchmark package for it (`~/checkout/oh-my-pi/packages/typescript-edit-benchmark/`). I did not find a result in the clones that proves it beats string replace for the model the tester uses, so treat the benefit as unverified for this gateway.

Permissions. A Claude Code setup in `bypassPermissions` with deny rules and PreToolUse hooks makes the practical comparison is "the deny rules and hooks" versus nothing (Pi) or OMP's yolo default. OMP can be configured to `write` or `always-ask` modes, which is closer to Claude Code's behaviour than anything in Pi without writing an extension. OMP's approval tiers are coarse (the whole `bash` tool is `exec`; only a "critical command" override raises a prompt for specific commands) and cannot express `Bash(git push *)`-style patterns per the docs I read; I did not find a pattern language.

Hooks. Neither Pi nor OMP runs Claude's settings.json shell hooks. A Claude hook is a command receiving JSON on stdin; porting means a small extension that shells out to the same scripts from `tool_call` and maps exit codes to `{ block: true, reason }`. Both `tool_call` handlers can block (PI/extensions.md line 218, OMP/extensions.md line 86). This is feasible but is not done (PORTING.md).

Telemetry. Pi's `enableInstallTelemetry` defaults to true; for an enterprise-managed machine set `PI_TELEMETRY=0` and `PI_OFFLINE=1` before any real use. I did not trace what OMP sends on startup (update checks, catalog refresh); unverified.

Maintenance. The Pi clone's low commit count conflicts with a project this size, so I would not read it as low activity without checking whether the clone is shallow (`git rev-parse --is-shallow-repository` was not run).

## Where each wins

**Claude Code**
- Claude Code already has a whole safety layer: hooks, deny rules, allowlist patterns, `--restricted`, `--permission-prompts none` for headless.
- Mature headless surface: `--json-schema`, `--max-budget-usd`, `stream-json` input and output, hook events in the stream, `--fallback-model`.
- Background sessions as a first-class feature (`--bg`, `attach`, `logs`, `stop`, `agents`), plus worktrees, cloud and Remote Control sessions.
- Anthropic first-party model behaviour: tools and prompt are tuned for Claude models, and prompt-snapshot flags keep the cache byte-stable across resume.
- Plugins, marketplaces and the existing many-skill, MCP and statusline setup need no porting.
- Lowest integration risk: the thing the tested other local tooling (hooks, statusline, auto-memory, handoff) is built around.

**Pi**
- Lowest overhead and smallest prompt, by far (FINDINGS.md numbers; roughly 2k tokens of prompt and schema by my estimate), which also means less prompt for the model to misread.
- Small, readable codebase and a documented extension API: every missing feature is an extension you control, with fail-closed `tool_call` blocking.
- Tree-structured sessions with `/tree`, `/fork`, `/clone`, HTML export; easy to reason about.
- Broadest-by-simplicity provider support and custom providers through `models.json`, including local llama.cpp.
- Clean embedding story: SDK, JSONL mode and RPC all share one agent loop; MIT.
- Cache warming and declared cache lifetimes are designed for cost control.

**OMP**
- Most built in: subagents with worktree isolation, LSP, AST grep/edit, browser, python, plan mode, goal mode, memory backends, approval tiers; nothing to write.
- Hashline edits with an Rust-native edit engine and per-model edit variants.
- Model roles (`smol`, `slow`, `plan`) with fallback chains and prewalk, which let cheap models do execution after a strong model plans.
- Session robustness: `--restore` after a crash including subagents, import of Claude Code and Codex sessions (`--from-claude`), machine-to-machine session handoff.
- Approval modes that can be tightened (`always-ask`, `write`) without code; ACP server for editors; very active development (2252 commits in 90 days).
- Reads `.claude/` skills, MCP, context files natively, so it picks up more of the tested setup than Pi does.

## Risks of adopting Pi or OMP

- **Safety hooks do not run.** Safety hooks (timeout, read and git guards, for example) are shell commands in Claude's JSON contract; neither harness executes them (PORTING.md). Until ported to `tool_call` extensions, destructive Bash and writes to protected paths are unguarded.
- **No permission prompts, and the deny list is not honoured.** Pi has none by design (PI/security.md). OMP defaults to `yolo`. Claude-style deny and allow rules have no equivalent in either (PORTING.md). Claude Code in bypass mode is only tolerable because of its deny rules and hooks.
- **No sandbox.** Both run with the full account permissions; Pi's docs say the only real boundary is a container or VM, and no sandbox wrapper was used in the test. Extensions are not sandboxed either (OMP/extension-loading.md).
- **Pi lacks subagents, plan mode, memory, LSP, web tools and background jobs.** Workflows that use the Agent tool, `run_in_background`, handoff and auto-memory have no drop-in.
- **OMP costs more than Claude Code while streaming and holds about 1 GB RSS per TUI** (FINDINGS.md), and is a very large, fast-moving codebase (Rust crates, Bun runtime, 100 KB of tool prompts), so a bug or prompt change can land weekly. Pin the version.
- **Telemetry and update behaviour.** Pi's install telemetry is on by default; both phone home for model catalogs or updates unless offline flags are set. Check against the organisation's policy before use.
- **Model-fit risk.** Both are tuned for many providers; Claude-specific behaviour (prompt snapshots, effort levels, tool-use quirks of an enterprise gateway) is less exercised. The pilot already saw a Pi stream hang (1 of 3 runs) and Claude's gateway warnings; neither Pi nor OMP has been tested on a realistic edit loop with guards (FINDINGS.md next step 4).
- **MCP project-config trust.** Pi gates project `.pi/mcp.json` behind trust, but context files (`AGENTS.md`, `CLAUDE.md`) load without it (PI/security.md), so prompt injection through a cloned repo is unmitigated in both.
- **Unverified items above.** Claude Code's bare prompt size, edit semantics and telemetry, OMP's default network calls, and Pi's shallow-clone question should be checked before a decision rests on them.
