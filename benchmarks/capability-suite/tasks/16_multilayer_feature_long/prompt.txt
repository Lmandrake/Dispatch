We want recurring issues in trellis: an issue like "Weekly status report" with a rule such as "every 2 weeks on mon,thu until 2027-01-01" that, when closed, spawns its next occurrence automatically. The agreed design is docs/RECURRENCE.md; treat it as the specification and implement all of it end to end: the rule grammar and date rules (new module trellis/recurrence.py with canonicalize and next_due), the model fields, spawning on close, the Tracker methods and permission rules, a new storage version for both the JSON file format and the SQLite schema, the query-language fields, and every CLI, export, import, report, digest, timeline and db check change the document lists.

Keep everything that exists working. Data files and databases written by every earlier version of trellis (versions 1 to 4; samples are in tests/data/) must still open and upgrade, and the JSON and SQLite backends must keep behaving identically, including after a failed operation is rolled back. The other docs in docs/ describe how the existing layers fit together and what each one expects of a change like this; read them, and the code they point to, before you start. Update the visible tests where the new output legitimately changes them, and add tests for the new behaviour. Standard library only; run the tests with python3 -m pytest -q.
